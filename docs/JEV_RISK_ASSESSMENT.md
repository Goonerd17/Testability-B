## 1. 평가 목적과 범위

**목적.** 실험 B에서 테스트를 작성하기 전에, 실제 구현된 메서드마다 테스트 필요성과 위험도를 Jev로 평가해 테스트 작성 우선순위를 정한다. 이 결과는 Phase 5(테스트 작성)의 입력이 된다.

**범위.**

- 평가 자료: `docs/BUSINESS_RULES.md`, `docs/DOMAIN_MODEL.md`, `docs/TEST_CASE_MATRIX.md`, `docs/OPEN_QUESTIONS.md`, `docs/EXPERIMENT_SCOPE.md`, 그리고 `billing` 패키지의 프로덕션 클래스 4개
- 실험 A의 디렉터리·브랜치·테스트·결과 문서는 열람하거나 참고하지 않았다
- 이번 Phase에서 하지 않은 것: 프로덕션 코드·명세 수정, 테스트 코드 작성, 테스트·JaCoCo·PIT 실행
- 이 문서의 점수는 **테스트 필요성에 대한 사전 판단**이다. 실제 결함 존재 여부나 테스트 결과를 뜻하지 않는다

### 3.2 각 항목에 넣은 입력 (J-03 ~ J-05 공통)

모든 메서드에 같은 형식을 썼다. Claude의 판단(예: "이 메서드는 위험하다")은 넣지 않고 원문 근거만 넣었다.

1. 메서드 소스 원문(Javadoc 포함)과 메서드가 쓰는 상수·enum 상수 선언

## 5. 점수 환산 공식과 기준 (평가 전 확정)

### 5.1 Jev 원시 출력

`jev_score`는 항목마다 다음 값을 돌려준다(J-02 형식 확인 호출로 확인).

| 필드 | 의미 |
|------|------|
| `score` | 레벨 척도 위의 위치. 레벨이 n개면 **0 ~ n−1**이며, 두 레벨 사이의 소수값일 수 있다 |
| `level` | 가장 가까운 레벨 번호 (0부터) |
| `probabilities` | 레벨별 확률 분포 |
| `confidence` | 판단 확신도 (0 ~ 1) |
| `decision` | `auto`(confidence ≥ `auto_accept`) 또는 `review` |

Jev는 40/35/25점 배점을 지원하지 않는다. **배점 환산은 Claude가 아래 공식으로 계산한 값이며 Jev의 원시 출력이 아니다.**

### 5.2 평가 차원과 레벨 (3개 차원 × 5레벨, 0 ~ 4)

각 차원을 별도 `jev_score` 호출 1회로 평가하며, 모든 메서드를 한 호출에 함께 넣는다(같은 기준 적용).

**업무 영향도 (Business Impact)** — 질문: "이 메서드에 결함이 있으면 회원 등급이나 수수료 정산 결과에 얼마나 큰 영향을 주는가?"

| 레벨 | 설명 |
|------|------|
| 0 | 결함이 있어도 등급·수수료·정산 결과 값에 영향이 없다 |
| 1 | 결함이 즉시 예외 등으로 드러나거나 간접적이어서 등급·수수료 금액이 조용히 틀릴 일은 거의 없다 |
| 2 | 드문 입력에서 결과 기록 항목이나 계산 허용/거부 판단이 틀릴 수 있지만 등급·수수료 금액은 대부분 정확하다 |
| 3 | 특정 경계값이나 조건에서 회원 등급 또는 수수료 금액이 틀리게 계산된다 |
| 4 | 대부분 또는 모든 정산에서 등급 또는 수수료 금액이 틀리게 계산되어 회원 전체의 청구액이 잘못된다 |

**오류 발생 가능성 (Error Likelihood)** — 질문: "이 메서드에서 경계값, 조건문, 날짜, 금액 계산 등으로 인해 명세와 다른 동작(결함)이 생길 가능성이 얼마나 높은가?"

| 레벨 | 설명 |
|------|------|
| 0 | 분기나 계산이 없는 단순 반환·대입이라 잘못 구현될 여지가 거의 없다 |
| 1 | 단순한 로직이며 경계값·날짜·금액 계산이 거의 없다 |
| 2 | 경계값 비교나 날짜·금액 계산이 하나 있어 off-by-one이나 단위 실수 가능성이 있다 |
| 3 | 경계값 비교, 시간대·월 경계, 반올림, 오버플로 중 둘 이상이 얽혀 실수 가능성이 높다 |
| 4 | 여러 경계·시간대·반올림·오버플로 조건이 결합되고 명세 해석이 까다로워 실수가 생기기 매우 쉽다 |

**코드 복잡도 (Code Complexity)** — 질문: "이 메서드의 분기, 상태, 의존성, 입력 검증 복잡도는 어느 정도인가?"

| 레벨 | 설명 |
|------|------|
| 0 | 분기 없음, 의존성 없음, 값 반환이나 대입 한두 줄 |
| 1 | 분기 또는 입력 검증이 하나 정도이고 외부 의존성이 없다 |
| 2 | 분기 2 ~ 3개 또는 반복문 하나가 있고 JDK 시간·수치 API를 사용한다 |
| 3 | 반복문과 조건이 결합되거나, 다른 메서드 여러 개를 호출하거나, 시간대 같은 환경 요소에 의존한다 |
| 4 | 여러 단계를 조율하고, 주입된 Clock 같은 외부 상태에 의존하며, 여러 분기·예외 경로와 다른 메서드 다수를 조합한다 |

### 5.3 환산 공식

```
영향도 점수   = 40 × (impact.score     ÷ 4)
가능성 점수   = 35 × (likelihood.score ÷ 4)
복잡도 점수   = 25 × (complexity.score ÷ 4)
위험도 합계   = 영향도 점수 + 가능성 점수 + 복잡도 점수   (0 ~ 100)
```

- `score`는 Jev가 돌려준 값을 그대로 쓴다(`level`로 반올림하지 않는다).
- 차원별 점수와 합계는 소수 첫째 자리까지 표기한다(표기용 반올림, 정렬은 반올림 전 값 기준).
- 모든 메서드에 같은 공식을 적용한다. 메서드별 가중치 보정이나 수동 조정은 하지 않는다.

### 5.4 위험 등급과 순위 규칙

| 위험 등급 | 합계 |
|-----------|------|
| 높음 | 70 이상 |
| 중간 | 45 이상 70 미만 |
| 낮음 | 45 미만 |

- 순위는 합계 내림차순. 동점이면 영향도 점수 → 가능성 점수 순으로 높은 쪽을 앞에 둔다.

### 5.5 불확실성 처리

- 세 차원 중 하나라도 `decision = review`(confidence < 0.7, 기본 `auto_accept`)이면 해당 메서드의 합계를 **잠정**으로 표시한다. Claude가 레벨을 임의로 바꾸거나 확정하지 않는다.
- 잠정 항목은 확률 분포에서 확률이 0.2 이상인 가장 낮은 레벨과 가장 높은 레벨로 계산한 **합계 범위**를 함께 기록해, 순위가 바뀔 수 있는지 보인다.
  - (평가 후 보충) 범위를 계산할 때 `auto`인 차원은 `score`를 그대로 고정하고, `review`인 차원만 레벨 범위로 바꿔 계산했다. 범위는 주요 레벨 기준이라 `score`(기댓값)가 범위 밖에 있을 수 있다(예: M05).
- 보조 순위(`jev_rank`)는 환산 점수에 섞지 않고 교차 확인용으로만 사용한다. 주 순위와 크게 다르면 §9에 기록한다.

## 10. Jev 평가의 한계

1. **정적 텍스트 판단이다.** Jev는 코드를 실행하지 않았다. 점수는 "결함이 있을 법한 정도"에 대한 판단이며, 실제 결함 유무나 테스트 결과와 무관하다.
2. **확신도가 낮다.** 33개 판단 중 22개가 `review`였고, confidence 0.00인 판단도 3개(M01 영향도, M03 영향도, M11 복잡도) 있다. 순위 1 ~ 2위를 뺀 중간 순위는 합계 범위가 서로 겹쳐 순서를 단정할 수 없다.
3. **레벨 정의는 Claude가 작성했다.** 레벨 문구가 결과에 직접 영향을 준다. 특히 복잡도 레벨 0("한두 줄")과 레벨 3("시간대 같은 환경 요소에 의존")이 한 줄짜리 시간 변환 메서드(M10, M11)에 동시에 들어맞아 분포가 갈렸다.
4. **메서드 단위의 한계.** 위험이 메서드 로직이 아니라 데이터(enum 상수 표)에 있는 경우(M03, M02) 메서드 단위 평가로는 잘 드러나지 않는다. 반대로 M06처럼 다른 메서드를 조합하는 메서드는 하위 메서드의 위험을 함께 반영해 점수가 높게 나올 수 있다.
5. **입력 구성의 영향.** 항목에 관련 Rule ID와 호출 관계를 넣었다. 이 정보가 판단을 특정 방향으로 이끌었을 수 있다. J-06은 J-03 ~ J-05보다 축약한 코드를 썼다.
6. **한 번만 실행했다.** 같은 입력을 반복 호출했을 때 결과가 얼마나 달라지는지는 측정하지 않았다.
7. **배점은 Jev 기능이 아니다.** 40/35/25 배점과 위험 등급 기준(70/45)은 Claude가 정한 환산 규칙이다. 다른 환산 방식(예: `level` 사용, 최빈 레벨 사용)을 쓰면 순위가 달라질 수 있다.
8. **명세와 코드의 대응은 확인하지 않았다.** 이번 평가는 테스트 필요성 평가이며 코드 리뷰가 아니다. 코드가 명세를 지키는지는 Phase 5 이후 테스트로 확인한다.
